A: A notice that a parcel arrived triggers several independent tasks. The notice describes something that happened; it is different from an instruction ordering a specific worker to act. Events and commands should preserve that distinction.
M: Commit domain state and an outbox row in the same local transaction. A relay publishes the row and marks progress; it can publish twice after a crash. Consumers use an inbox or unique event ID to apply local changes atomically. Carry entity version to detect stale or out-of-order events and trace IDs to connect the workflow.
W: Order O and outbox event E commit together. The relay publishes E but crashes before recording success. It republishes E after restart. Inventory's unique inbox ID rejects the duplicate while the valid first delivery reserves stock once.
T: Events support asynchronous fanout and independent scaling. Direct RPC is easier for immediate queries and small workflows. Event sourcing stores state as an event history; using events for integration does not require event sourcing.
F: Writing the database then publishing without an outbox loses events between the two steps. Publishing before commit can announce rolled-back state. Long event chains can hide cycles and unbounded work; document ownership and terminal states.
D: Local atomicity plus replay does not instantly produce global consistency. Expose pending states and reconciliation jobs. A healthy broker and healthy consumers can still produce an incorrect system if event semantics disagree, versions are reordered, or one subscription silently stops advancing.
X: Crash a relay after publish and verify one inventory change. Delay event version 2 until after version 3 and define stale handling. Draw the full order workflow including compensations, ownership, and a timeout for stuck intermediate states.

@@18|Distributed Transactions
E: A distributed transaction coordinates changes across multiple transactional participants. ShopStream might need inventory and billing to agree on a commit decision. Independent local commits cannot guarantee all-or-nothing behavior when a process or network fails between them.
A: Two departments reserve resources, then wait for a coordinator's final approval. If the coordinator disappears, reservations remain uncertain. Real protocols need durable decision records rather than informal promises.
M: In two-phase commit, a coordinator asks participants to prepare. Each participant durably records readiness and holds required resources. If all vote yes, the coordinator durably records commit and sends that decision; otherwise it aborts. Participants recover using their logs and the coordinator decision. A prepared participant may block when it cannot learn the final outcome.
W: Inventory prepares a reservation and billing prepares a ledger entry. The coordinator records commit, then loses connectivity before notifying billing. Billing must not guess abort simply because of a timeout; recovery must obtain the durable decision and finish commit.
T: A single-database transaction is usually simpler and should be preferred where the data boundary permits it. Two-phase commit preserves atomic outcome across supporting participants but adds latency and availability coupling. Sagas instead use committed steps and semantic compensation.
F: Calling two REST APIs inside a local SQL transaction does not create a distributed transaction. Holding locks during slow remote calls increases contention. A transaction timeout is not always permission to reverse a participant that already prepared.
D: Atomic commit and consensus solve related but different problems. Consensus can replicate a coordinator's decision, yet every participant must still honor its transaction protocol and recover durable state. ACID isolation also needs explicit treatment; atomic outcome alone does not prevent every concurrent anomaly.
X: Write a prepare/commit timeline for two participants. Stop the coordinator after recording commit and derive each recovery action. Redesign the same purchase as a Saga and identify the weaker isolation and customer-visible pending state.
V: Begin cross-system change|Ask participants to prepare|All prepared?|Persist commit decision|Persist abort decision|Notify and recover participants|Resolve atomic outcome

@@19|Saga Pattern
E: A Saga implements a business workflow as local transactions with compensating actions. ShopStream reserves stock, requests payment, and confirms an order without holding one database transaction across services. If a later step fails, earlier effects need business-specific correction.
A: A travel agent books a flight and hotel separately. Cancelling a flight can incur a fee and cannot undo the historical booking. Compensation similarly repairs business state rather than erasing time.
M: Persist a workflow ID and current state. Execute each step with an idempotency key, record its outcome, and advance only after a known result. On failure, run compensations in a suitable dependency order, retrying them durably. Orchestration uses a coordinator; choreography lets events trigger steps. Both require deadlines, deduplication, and reconciliation.
W: Reserve inventory succeeds. Payment is declined, so release inventory and mark the order rejected. If payment times out, first reconcile the payment ID; immediately releasing stock and later discovering a successful charge creates a paid-but-unfulfillable order.
T: Sagas avoid long cross-service locks and accommodate heterogeneous APIs. They expose intermediate states and require careful compensation. A refund is not identical to an uncharged payment, and some actions, such as sending an email, are not reversible.
F: Treating compensation as guaranteed success leaves stuck workflows. Missing persistence loses progress on restart. Concurrent Sagas can violate invariants unless reservations, version checks, or semantic locks protect shared resources.
D: Choose a pivot after which the workflow should roll forward rather than compensate. For shipping, dispatch may be such a point. Define manual repair for irrecoverable cases and monitor age by workflow state; aggregate service health cannot reveal every stuck business transaction.
X: Simulate payment decline and assert inventory is released once. Fail the compensation and persist a retry. Design a reconciliation view listing workflow ID, last successful step, unknown outcomes, and safe operator actions.
V: Start durable workflow|Reserve inventory|Payment confirmed?|Confirm order|Reconcile or compensate|Persist recovery progress|Finish or escalate repair
